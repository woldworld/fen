## 0. 结论先行

1. **能做，而且在现架构内改动集中**：邮件 = 注册表里的**一组工具**，不是内置邮件服务器，
   也不是内置邮箱界面。零新增管线，权限/审计/热插拔全部复用既有机制。
2. **"要不要 Google 认证"不是必答题，取决于凭据归谁**（见 §1）：
   - 用**应用专用密码**（不走 OAuth）⇒ **没有认证这回事**，Google 根本不知道有我们。
   - 用**用户自己的 client_id**（BYO）⇒ 审核对着**用户的项目**，我们只发代码，**我们零负担**。
   - 用**我们出厂的 client_id** ⇒ 才需要认证，且 100 用户上限挡的是我们的用户。
   ⇒ 我们**现在只需要 ①②**，不需要的是 ③。这一点与用户判断一致。
3. **★ 已按「数据只在用户手机端、我们不代理」定案**（判据＝PRD §9.1「服务器有没有变成保管人？」）：
   - **出口＝设备直连**，Hub 代理 **⛔ 不做**（会让我们成为保管人/中转方）。
   - **凭据＝① 应用专用密码 + IMAP/SMTP 为默认**：零 Google 审核、本周可跑、
     **大众用户能照做**（OAuth 无论谁的 client_id 都要求普通人建 Cloud 项目或绕 7 天掉线，做不到）。
   - **(b) BYO OAuth 作为技术用户的进阶选项**写进文档；**(c) 出厂 client_id ⛔ 现在不做**。
   - ★★ **新增硬约束：邮件能力与「试用代调」互斥**（见 §2.2）——否则试用用户读信时，
     邮件正文会经我们的服务器转发给模型 = 事实上代理。
4. **落地前必须先修 3 处既有接线缺陷**（§3.4）。不修就会踩：发信"每次弹窗"的承诺被白名单打破、
   **邮件正文与收件人全量明文落库**、敏感档弹窗把网络能力误报成本地能力。

## 1. 前置事实：审核落在**谁的**头上，由"谁的 client_id"决定

> ★ 本节的判据轴不是"用哪种接口"，而是**这个 OAuth 客户端是谁注册的**。
> 同一个 Gmail API，用户自带 client_id 时审核对着用户的项目，出厂 client_id 时审核对着我们。
> （2026-10-08 查证；主要来源 Google 官方 OAuth2 文档与 Workspace 政策页，**非记忆**）

### 1.1 三种凭据归属 × 审核归属

| # | 凭据归属 | 认证方式 | **Google 审核落在谁头上** | 用户要做什么 | 结论 |
|---|---|---|---|---|---|
| **①** | **用户自有** | **应用专用密码 + IMAP/SMTP** | **无审核可言**——不走 OAuth，不存在同意屏，Google 也不知道有我们 | 开两步验证 → 生成 16 位码 → 粘贴 | ★ **本方案第一阶段，唯一对大众可用的零审核路径** |
| **②** | **用户自有** | OAuth（用户自建 Cloud 项目，自带 client_id） | **落在用户自己的项目上**；自用不验证也能跑通（见 1.2 两个坑） | 建 Cloud 项目 → 配同意屏 → 授权 | ★ 第二阶段，面向**技术用户/自建者** |
| **③** | **我们出厂** | OAuth（一个 client_id 服务所有用户） | ❌ **落在我们头上**：应用验证 2–4 周；通过前**「未验证应用」警告 + 100 用户上限** | 点"用 Google 登录" | ⛔ **现在不做**。Muse 走的是这条 |
| ④ | 第三方（Unipile / Nylas 等） | 他们代持并已持证 | 免（他们承担） | 点登录 | 付费；**邮件过第三方服务器** |

**已死路径**：基本密码登录（个人 Gmail 2022-05 停；Google Workspace **2025-03-14** 全面停）。
"安全性较低的应用"开关已移除。

**受限范围的代价（仅 ③ 需要关心，但列出来封死这条路）**：申请 `mail.google.com`
（= 完整 IMAP 级）属受限范围 ⇒ **CASA Tier 2 审计**（2026 自助路径约 $540–1000）。
⚠️ 各 scope 的敏感/受限分档**各方资料不一致**（`gmail.compose` / `gmail.modify` 是否受限说法有冲突）
⇒ 以 **Cloud Console 实际标注**为准，不要照抄任何名单。

### 1.2 ② 的两条必须写进文档的坑（用户自带 client_id 也不是无痛）

1. **发布状态留 `Testing` ⇒ 刷新令牌 7 天过期。**
   Google 官方 OAuth2 文档原文：外部用户类型 + 发布状态"测试"的项目，其刷新令牌**七天后过期**
   （除非只申请 name/email/profile 基础范围）。症状 = agent「每周莫名掉线」。
   ⇒ 让用户把发布状态改成 **`In production`（可以不完成验证）**：同意时出现一次
   "未验证应用"警告，点"高级 → 继续"即可，**令牌变长久**；代价是该项目 **100 用户上限**——自用完全够。
2. **同一 Google 账号 + 同一 client_id 最多 100 个刷新令牌**，超限会**静默吊销最老的那个**。
   ⇒ 客户端**不要**每次重连都重新走一遍授权（否则表现为"随机被撤销"）。

**另有一条免税通道**：若用户的邮箱在 **Google Workspace** 组织内，同意屏可设
**`Internal` 用户类型** ⇒ **完全不触发验证**，且无 7 天问题。
`wold.world` 是我们自己的域名 ⇒ 我们自己这条账号就能走 Internal。

---

**③ 路线上另有两条硬规定**（现在与我们无关，但记下来以封死幻想）：
- **禁止**开多个 Cloud 项目把用户分散到各项目以规避 100 人上限 —— 会被封号。
- 受限范围**要求实施提示注入防护**（Model Armor 或等效）。
  ⇒ 我们已有的 `_wrapUntrusted`（`lib/core/agent_service.dart:197`）正好对上，是加分项。

> ⚠️ **应用专用密码的代价（必须对用户明说）**：它是静态凭据，**绕过两步验证**，
> 一旦泄漏 = 长期可读可发，直到用户手动吊销；Google 自己把它定性为"遗留设备的过渡方案"。
> Google Workspace 账号**默认禁用**，需管理员开启。

## 2. 架构决策：出口放设备，不放 Hub

> ★ **决定性判据来自 PRD §9.1 原文**（`大荒AI产品需求说明书与行动计划.md:889`）：
> 「**判据（对任何"新的钥 / 数据流转路径"一律先问）：服务器有没有变成保管人？**」，
> 以及同页 888 行：「**不打开系统云备份/D2D**（那等于**静默引入第三方**）」。
> 本方案的两项选择（凭据形态、出口位置）**全部由这一条推导**，不另立标准。

### 2.1 由该原则直接推出的四条硬约束

1. **凭据与邮件正文的存储，任何一环都不得落到我们的服务器**（服务器不得成为保管人）。
2. **凭据只放设备安全存储**（Keystore / Keychain）；明文**绝不**入库、**绝不**进审计、**绝不**进日志。
3. **不得为"以后方便"预留服务端中转**——PRD 反对的正是"**静默**引入第三方"。
   要引入就当作一次显式产品决策单独过。
4. ★★ **邮件能力必须与「试用代调」互斥**（下节详述）。这条最容易被忽略，但它是原则的必然推论。

### 2.2 ★★ 与「试用代调」的冲突（本方案最重要的一条约束）

PRD §7 的试用代调（`hub.js` `TRIAL_TURN_LIMIT` = 20 轮）把**模型调用**经我们的服务器转发。
而"读信"这条链是：`邮件正文 → 进上下文 → 发给模型`。两者一叠加：

> **试用用户只要读过一封邮件，那封邮件的内容就会经由我们的服务器转发给模型服务商。**
> 不是"保管"，但**在事实与用户感受上，我们成了邮件内容的中转方**——与"我们不代理"的对外承诺冲突；
> 且在 GDPR/CCPA 口径下，把用户邮件内容转交第三方模型服务商属于**必须明示的处理行为**
> （PRD 已写「明示用途」，`…:887`）。

**处置（二选一，推荐前者）**：
- **(推荐) 邮件工具只对「自备模型 Key」的用户开放**。试用额度下邮件工具**不可见/被拒**，
  拒绝理由必须可见（不得静默失败——红线：静默失败要常驻说明）。
- 或：试用链路**只允许元数据**（`mail_list` 的标题/发件人/时间），**`mail_read` 正文在试用下禁用**。

**措辞纪律（对外文案不得越界）**：
- ❌ 不得写"邮件内容不离开你的手机"——它**要**经过模型（哪怕是你自己的 Key）。
- ✅ 准确说法："**邮件只存在你的手机，我们不保存任何副本**；内容仅在你授权下、
  交给你自己指定的模型处理。"

| | 设备直连（**唯一符合上述原则**） | Hub 代理（**违背原则，备查**） |
|---|---|---|
| 凭据位置 | 手机安全存储（Keystore/Keychain） | 服务器 |
| Google 年度第三方评估 | **不触发** | ★ **触发**：政策原文——凡"可从第三方服务器或透过第三方服务器存取"Google 用户数据的应用，**每年**须接受 Google 核准第三方机构的安全评估 |
| 隐私叙事 | 与"身份/数据归你自己"一致，可写进宣传 | 邮件内容过我们的服务器，须在隐私政策披露 |
| 能力上限 | 分身**只在 App 活着时**能读信（与 R10/R11「后台不拉会客厅 feed」同一取舍） | 可做实时推送、多端一致 |
| 结论 | ✅ **采用（唯一解）** | ⛔ **不做**——服务器成为保管人/中转方，违反 PRD §9.1 判据，无例外 |

> **代价照旧说清**：设备直连意味着分身**只在 App 活着时**能读信，做不到实时推送。
> 这是"不代理"原则的必然价格，不是实现缺陷——与 R10/R11「后台不拉会客厅 feed」是同一个取舍。

**协议层**：自己写 IMAP/SMTP 最小子集（零新依赖，走 `ctx.httpClient` 同源的 `dart:io`）。
不引第三方邮件库，理由：① 邮件库普遍体积大、且多绑 OAuth 流程；② 我们要的只是
"列/读/发/存草稿"，不需要完整客户端；③ 纯解析逻辑可做成纯函数单测（本项目已有此纪律）。

**代码放哪**：放 **`lib/core/mail/`（私有层）**，**不放 `packages/pocket_harness/`**。
理由：`pocket_harness` 在开源发布树里（白名单 `mustExist`），放进去等于**自动对外发布**；
且邮件接入是产品能力，非通用工具框架。可直接复用包里的公开函数 `htmlToText`（`builtin_tools.dart:237`）。

### 3.3 工具组与权限矩阵

| 工具 | 档位 | grantKey | 理由 |
|---|---|---|---|
| `mail_accounts` | `normal` | — | 本地只读，只看"绑了哪个号、连不连得上" |
| `mail_list` | `sensitive` | `mail:read` | 一次性授权、持久、可吊销 |
| `mail_read` | `sensitive` | `mail:read` | 同上（共键 ⇒ 一次授权整组生效） |
| `mail_draft` | `normal` | — | **只写本地草稿，不出网** ⇒ 真·本地能力 |
| `mail_send` | **`critical`** | — | 每次弹窗 + 每次写审计；**不可加入免弹窗白名单**（§3.4-①） |

★ 设计要点：**把"起草"与"发送"拆成两个工具**。让模型先产出 `mail_draft`（零风险、随便调），
再由主人对某一条草稿点"发"。这样"代管"的价值保留九成，而"AI 自己决定发出去"的风险归零。

### 3.4 ★ 落地前必须先修的 3 处既有接线缺陷

**① `critical` 档其实也会被白名单放行 ⇒ "每次弹窗"是假的**
`lib/harness_host/harness_permission_policy.dart:120-122`：
```dart
final allowlist = prefs.getStringList('tool_auto_allow') ?? const [];
if (allowlist.contains(tool.name)) return const Allow();   // ← critical 也走这里
```
一旦用户（或某条引导话术）把 `mail_send` 加进 `tool_auto_allow`，**此后发信再也不过闸**。
⇒ 必须在 `_confirmFlow` 里为 `mail_send` 之类加"禁止免弹窗"分支（不改这一条，发信闸就是装饰）。

**② `critical` 档的自动审计会把邮件正文全量明文落库**
同文件 `:133-141`：
```dart
draftText: '${tool.name} $args',     // ← $args 含 to/subject/整篇 body
```
`mail_send` 设为 critical 的同时，**整封邮件正文与收件人会被写进审计表**。这与
"凭据/隐私不落明文"的纪律直接冲突。⇒ 审计必须先过一层**参数脱敏**（只留收件人域名 + 主题 + 正文字节数）。

**③ `capabilitiesOf` 会把 `mail_*` 的网络能力误报为"本地"**
`lib/core/agent_service.dart:579-583`：查不到就回落 `const [PluginCapability.local]`。
内置工具**没有**登记能力（`_dbToolCaps` 只由 DB 工具与 MCP 填），
`mail_read` 用 sensitive 档时，弹窗会告诉用户"这是本地能力"——**说错了**。
⇒ 加一张 `_builtinCaps` 表并在闭包里查，`mail:read` 登记 `[PluginCapability.network]`。

> 附：**不要走 MCP 路线做这件事**。`_isPrivateOrLoopback`（`agent_service.dart:182-194`，判定点
> `:883`）拒绝 `localhost` / `127.*` / `10.*` / `192.168.*` / `169.254.*` / `172.16-31` ⇒
> 自建在本机或局域网的邮件 MCP 服务**连不上**，必须公网 https 端点。

## 4. 数据模型（v37）

```sql
-- 账号（凭据密文不在这里，在安全存储）
CREATE TABLE IF NOT EXISTS mail_accounts (
  id TEXT PRIMARY KEY, address TEXT NOT NULL, display_name TEXT,
  imap_host TEXT NOT NULL, imap_port INTEGER NOT NULL DEFAULT 993,
  smtp_host TEXT NOT NULL, smtp_port INTEGER NOT NULL DEFAULT 465,
  security TEXT NOT NULL DEFAULT 'tls',   -- tls | starttls
  enabled INTEGER NOT NULL DEFAULT 1,
  last_ok_at INTEGER, last_error TEXT, created_at INTEGER NOT NULL);

-- 已读游标（避免重复把同一封信喂给模型）
CREATE TABLE IF NOT EXISTS mail_seen (
  account_id TEXT NOT NULL, uid TEXT NOT NULL, seen_at INTEGER NOT NULL,
  PRIMARY KEY (account_id, uid));

-- 出站台账（草稿 + 已发送；★ 不存正文全文，只存摘要与前 256 字预览）
CREATE TABLE IF NOT EXISTS mail_outbox (
  id INTEGER PRIMARY KEY AUTOINCREMENT, account_id TEXT NOT NULL,
  status TEXT NOT NULL,                   -- draft | sent | failed
  to_addrs TEXT NOT NULL, subject TEXT, preview TEXT,
  error TEXT, created_at INTEGER NOT NULL, sent_at INTEGER);
```
迁移规矩照旧（`db_helper.dart:41-55`）：建表一律 `IF NOT EXISTS`、播种一律 `ConflictAlgorithm.ignore`，
所以"降级→再升级"会重新收敛。

## 5. 工作量与风险

| 模块 | 规模 | 难点 |
|---|---|---|
| `imap_client.dart` | **400–700 行** | IMAP **literal（`{n}`）解析**是唯一真难点；需处理分块到达、CRLF、`+` 续行 |
| `smtp_client.dart` | ~150 行 | 相对简单；注意 465 隐式 TLS vs 587 STARTTLS 别混 |
| `mime_codec.dart` | ~200 行 | **纯函数 ⇒ 可单测**，是测试投入产出最高的部分 |
| 绑定页 + i18n | ~300 行 + 五语种 | arb 五份齐改 |

| 风险 | 说明 | 对策 |
|---|---|---|
| 凭据泄漏 | 应用专用密码**绕过 2FA**、长期有效 | 安全存储 + 一键"断开并吊销"引导 + 明文绝不入库 |
| 误发 | AI 代表你发信 | 起草/发送拆开 + critical 每次弹窗 + 出站前回显收件人 |
| 提示注入 | 邮件正文是头号载体 | 进模型前 `_wrapUntrusted`（`agent_service.dart:197`） |
| Google 政策变动 | 应用专用密码是"过渡方案"，随时可能收紧 | 协议层与认证层解耦 ⇒ 将来换 OAuth 只改认证，不动 IMAP/SMTP |
| BYO OAuth 的 7 天掉线 | 用户自建项目留在 `Testing` ⇒ 刷新令牌 7 天过期，症状是"每周莫名掉线" | 文档明写：发布状态改 `In production`（可跳过验证，接受一次未验证警告）；客户端对 `invalid_grant` 要有重授权引导 |
| 刷新令牌被静默吊销 | 同一账号 + 同一 client_id 满 100 个令牌会静默吊销最老的 | 客户端不得每次重连都重新授权；令牌持久化在安全存储，不重复换取 |
| Workspace 账号 | 管理员默认禁应用专用密码 | 绑定页明说失败原因，给"请管理员开启"提示 |
| 权益红线（PRD §9.1） | 权益不得可转让/兑现 | 邮箱是**主人自有资产**，不得出现"邮箱/收件箱可转让、可出售、可挂钩收益"的字段与接口 |

## 7. 决策与待拍板

### 7.1 已定（依 PRD §9.1 判据推导，2026-10-08）

| 项 | 决定 | 依据 |
|---|---|---|
| 出口 | **设备直连**，不做 Hub 代理 | 服务器不得成为保管人；不做"静默引入第三方" |
| 凭据 | **应用专用密码 + IMAP/SMTP**（默认）；BYO OAuth 为进阶；出厂 client_id ⛔ | 零审核 + 大众可用 + 跨厂商 + 服务器零接触 |
| 凭据存储 | 设备安全存储，明文不入库/不入审计/不入日志 | 同 §3.4-② |
| 与试用代调 | **互斥**（试用用户禁用正文读取，或整体禁用邮件工具） | §2.2：否则邮件正文经我们服务器转发＝事实代理 |
| 对外措辞 | 不说"邮件不离开手机"，说"我们不保存副本" | §2.2 措辞纪律 |

### 7.3 附：三形态对比（备查，勿删）

- **(a) 应用专用密码 + IMAP/SMTP** —— 零审核、本周可跑、**大众用户能照做**；
  代价是用户要开 2FA 并粘贴 16 位码，且凭据是静态长效（靠安全存储 + 一键吊销兜）。
  **⇒ 选定为默认。**
- **(b) BYO OAuth（用户自带 client_id）** —— 零审核、体验好；代价是**只有技术用户做得来**，
  且必须写清 7 天掉线坑与 100 令牌上限。**⇒ 保留为进阶选项。**
- **(c) 我们出厂 client_id** —— 体验最好、大众可用；代价是**我们**要吃 2–4 周应用验证 +
  100 用户上限（与推广目标直接冲突）。**⇒ 现阶段不做**；等真有用户量、且愿意承担合规责任时再单独决策。

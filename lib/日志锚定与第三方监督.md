# 日志锚定与第三方监督（§16 配套设施）

> 配套代码：`lib/core/log_anchor.dart`、`tool/anchor_log.dart`、`tool/verify_log_anchor.dart`。
> 上游：PRD §16「可验证性：闭源信任层的补位机制」。

---

## 1. 为什么需要"锚定"

`lib/core/transparency_log.dart` 的哈希链能挡住两类作恶：

| 作恶方式 | 为什么挡得住 |
|---|---|
| **改写**某条历史记录 | 该条目的 `hash` 变了，其后所有条目的 `prev_hash` 全部对不上 |
| **中段删除** | 被删条目之后的 `index` / `prev_hash` 立刻错位 |

但它**原理上挡不住第三类**：

| 作恶方式 | 为什么挡不住 |
|---|---|
| **截断**（砍掉末尾若干条） | 剩下的前缀依然是一条**自洽**的链，`verifyChain()` 照样返回 `true` |

而"砍尾巴"恰恰是最省事的作恶方式——删掉对自己不利的最新记录，日志看起来一切正常。

**唯一的解法是把某一期的 `(size, root)` 写到日志自己管不到的地方**，之后无论 Hub 怎么改自己的存储，都对不上那份外部记录。这正是证书透明度（CT）里"Merkle root 定期锚定"的作用。

---

## 2. 三层防线

| 层 | 机制 | 挡住什么 | 代码 |
|---|---|---|---|
| ① 链式哈希 | 每条记录把 `prev_hash` 纳入自己的 `hash` | 改写、中段删除 | `transparency_log.dart` |
| ② 一致性证明 | 第 N 期是第 N−1 期的**前缀延续** | 用"另一棵看起来也自洽的树"冒充历史 | `MerkleVerify.consistency` |
| ③ **外部锚定** | 每期 `(size, root)` 写进日志管不到的地方 | **截断**（①②都查不出） | 本文件 / `log_anchor.dart` |

三者缺一不可：只有 ① 会被截断绕过；只有 ② 需要先有一个"可信的旧根"作为比对基准，而那个基准正是 ③ 提供的。

---

## 3. 锚定流程（操作手册）

### 3.1 例行锚定

```bash
# 从 Hub 抓当前 (size, root)，按 fail-closed 判据追加一行
dart run tool/anchor_log.dart emit --hub https://<hub-host> --note "周例行"
```

产物：
- `anchors/merkle_roots.jsonl` 追加一行：`{"size":…,"root":"…","anchored_at":…,"note":"…"}`
  （**只含规模与根，不含任何叶子/业务数据**，可安全公开。）
- 终端打印一份**锚定收据**，形如：

```
Wold transparency-log anchor
period       : 2026-09-28T00:00:00.000Z
tree_size    : 1234
merkle_root  : <base58>
prev_root    : <base58 或 (genesis)>
```

### 3.2 把锚定钉到外部（关键一步）

锚定文件只有落进一个**日志自己控制不了、且带可信时间戳**的载体才算数。两种载体：

| 载体 | 做法 | 时间戳来源 |
|---|---|---|
| **GitHub 签名提交**（PRD 指定） | 把收据粘进 commit message，commit 里带上 `anchors/merkle_roots.jsonl`，用 GPG/SSH **签名**提交 | 提交历史（第三方可查、不可事后伪造） |
| OpenTimestamps | 对 `anchors/merkle_roots.jsonl` 做 OTS 时间戳，把 `.ots` 一并提交 | 比特币区块链 |

> 为什么必须是**签名**提交：未签名的提交谁都能重写历史。签名提交把"这一期的根"与"某个不可回填的时间点"绑在一起。

### 3.3 校验

```bash
# 离线自检 + （给了 --hub 时）用一致性证明把相邻锚定与当前头全部连起来
dart run tool/anchor_log.dart verify --hub https://<hub-host>
```

## 4. fail-closed 判据

`AnchorPolicy.decide()` 在**追加之前**比对"这次观测到的 `(size, root)`"与"上一条锚定记录"：

| 情形 | 判定 | 退出码 | 含义 |
|---|---|---|---|
| 首次 | `append` | 0 | 创世锚定 |
| `size` 变大 | `append` | 0 | 正常推进 |
| `size` **变小** | `rollback` | **1** | 日志被回滚 / 截断 |
| `size` 不变、`root` **变了** | `fork` | **1** | 同样多的叶子长出两个根 = 历史被改写 |
| `size` 不变、`root` 相同 | `duplicate` | 0 | 幂等，不重复写 |
| 规模为负 / 根为空 | `invalid` | **1** | 输入非法 |

序列自检 `AnchorPolicy.validateSeries()`（`verify` 子命令）额外拒绝：规模倒退、同期换根、时间戳倒退、空根。

> **本工具只写不删**：不提供任何 remove / rewrite 子命令。任何"删掉某行让它通过"的操作都绕过整套机制。

## 5. 第三方监督流程（Monitor）

任何人（不必是用户、不必持有任何凭证）都能做监督者：

1. **下载日志**：`GET /api/log/leaves` → 得到全部叶子哈希列表（公开、匿名可读）。
2. **独立复算**：用任意语言按 RFC 6962 重算整棵树与任意一期根。
   - 字节口径见 `lib/core/transparency_log.dart` 头部注释与 `packages/protocol/src/log.js`。
   - 现成参考实现（Node，零依赖）：`packages/protocol` 导出的 `logRootAt` / `logInclusionProof` / `logConsistencyProof` / `logVerifyInclusionByHash` / `logVerifyConsistency`（见 `src/index.js`）。
3. **验自己的记录**：`GET /api/log/proof/inclusion/<index>` → 用包含证明确认"我的这条确实在日志里"。
4. **验历史未被改写**：`GET /api/log/proof/consistency?from=<旧期>&to=<新期>` → 用一致性证明确认"第 N 期是第 N−1 期的延续"。
5. **对锚定**：把当前根与本仓库 `anchors/merkle_roots.jsonl`（及签名提交历史）比对——**这是唯一能发现"截断"的一步**。

监督者不需要信任 Hub 的任何代码，只需要：一份叶子哈希列表 + 一棵按 RFC 6962 定义的树 + 一份外部锚定记录。

## 6. 诚实边界：这套机制**挡不住**什么

| 挡不住 | 说明 | 需要什么补 |
|---|---|---|
| Hub **一开始就不记录**某件事 | 日志只保证"记进去的改不了"，不保证"该记的都记了" | 客户端本地留存自己那份签名记录，事后可比对"我说过，你没记" |
| 客户端**不验** | 机制存在 ≠ 有人用；无人监督时锚定只是自说自话 | 把验证做进客户端关键路径（护照页的"离线验证"） |
| 锚定**频率**过低 | 两次锚定之间的截断仍不可见，直到下一次锚定 | 提高频率（原则：**锚定间隔内的操作量越小越安全**） |
| 锚定**载体**本身被夺 | 若 GitHub 账号被夺且未开签名保护 | 开强认证 + 强制签名提交；必要时并行发布到 OTS |

> 一句话：**这套机制把"你必须相信我"换成了"你可以随时验我，而且我篡改了也藏不住"。**
> 它不宣称零信任，它宣称**可证伪**。

## 7. 对应 PRD §16 的四行映射

| CT 的做法 | Wold 的实现 | 位置 |
|---|---|---|
| 公开只追加日志 | `/api/log/leaves` + 哈希链 | `hub.js` + `transparency_log.dart` |
| Merkle root 定期锚定 | `tool/anchor_log.dart` emit → GitHub 签名提交 / OTS | 本文件 |
| Monitor（任何人可监督） | 开放下载 + 包含/一致性证明验证器 | `verify_transparency_hub.js` |
| SCT（可验证凭证） | 每个身份拿到可离线验证的凭证 | `passport_screen.dart` 离线验证 |

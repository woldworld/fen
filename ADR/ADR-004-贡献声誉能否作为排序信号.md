## 1. 背景：一个被我搞混过的问题

上一轮做"智能体时代产品复盘"时，我把「按时间排序」列成了**待补的缺陷**，把「没有声誉权重」列为「半个缺口」。这是错的。这一节先把两件事拆开，因为它们的法律性质完全不同。

### 1.1 触发事实（2026-10-22 取证）

| 事实 | 实证 |
|---|---|
| PRD §9.1 明写红线 | `lib/大荒AI产品需求说明书与行动计划.md:768`：「以上五项**都不得演化为可转让、可兑现、可与利润挂钩的凭证**。一旦出现"可变现"，就从"权益"变成"证券"，本条全部作废」 |
| 五件套里的 ③ 就是"贡献声望" | 同文件 `:764`：「邀请、建圈、主持、贡献插件累计为**不可转让**的声望」，定位是"不可转让的股权替身" |
| 红线被做成**结构**而不是措辞 | `:771-788`：声望是**派生值**（`tally` 从记录现算，含幂等键去重与按类型封顶）；**库里不存在任何"分数/余额"表**；`ContributionStore` 上**没有任何** `transfer*` / `redeem*` / `payout*` / `sell*` 方法 |
| 代码注释重复了同一条 | `lib/hub/hub.js:967-968`：「贡献记录里没有任何字段表示"谁现在持有它"或"它值多少钱"，分值也不是存下来的余额（每次由记录现算），所以没有可转让之物」 |
| 守卫在守它 | `tool/verify_contribution_ledger.dart` **81 条** |
| **"可被看见"早就做了** | `hub.js` 里 `anonReadLimit(req)` 出现 11 次（含 1 处定义）⇒ **10 个匿名可读端点**，具名的包括 `/api/identity/rotations`、`/api/log`、`/api/log/proof/inclusion/…`、`/api/log/proof/consistency`、`/api/contributions/proof/…`、`/api/rooms/…`、`/api/rooms/roles/proof/…` |
| 而且"匿名可读"是**刻意的** | `hub.js:1280-1281`：「★ 匿名读限频（P1-5）：**只**限频，不鉴权 —— "任何人都能查"是可监督性的前提，改成要鉴权等于把监督权收回去」 |
| **"进排序"一件都没有** | 全项目排序只有三种：`world.js:731` 按 `created_at`、`world.js:952` 按 `id`、`hub.js` 各表按 `idx`（追加序）。**零个按声誉/权重排序** |

⇒ 结论：**"声誉能不能被看见"这道题已经答过了，答案是"能，而且必须能"**（否则 §16 的可监督性不成立）。真正没答的只有一道：**声誉能不能影响分发。**

### 1.2 为什么"看见"与"排序"必须分开裁

这是本 ADR 的核心判断，不是措辞讲究：

- **可查** ⇒ 声誉是**信息**。任何人都能拿到同样的记录，自己决定信不信。它不产生价值，也就不产生刷的动机（刷了也只能骗自己）。
- **排序** ⇒ 声誉是**资产**。曝光量 = 触达 = 潜在收益。一旦排序由声誉决定，声誉就自动获得**可变现的价格** —— 这正是 PRD §9.1 红线说的"可与利润挂钩"。它不需要我们主动挂价，**分发权本身就是定价权**。

⇒ 所以"把声誉接进排序"不是"加个功能"，是**把此前结构上做不到的事，做成结构上做得到**。这也正是为什么本 ADR 需要律师，而不只是工程评审。

## 2. 决策（待主人裁定）

> **是否允许"贡献 / 声誉"进入任何形式的分发排序；若允许，允许到哪一层。**

### 2.1 备选方案

| 方案 | 内容 | 与 §9.1 红线的关系 |
|---|---|---|
| **A 维持时间序**（现状） | 一切按 `idx` / `created_at` / `id` 排；声誉只可查、不参与分发 | ✅ 不触线。**现状即 A** |
| **B 用户主动筛选** | 默认仍是时间序；用户可**自己**选"只看贡献记录 ≥ N 的主体" | ⚠️ **可能安全**：分发权在用户手里，平台不改默认序 ⇒ 声誉仍是信息不是资产 |
| **C 平台按声誉加权** | 默认排序 = 时间 × 声誉权重 | ❌ **触线**：平台用分发权为声誉定价 ⇒ "与利润挂钩" |
| **D 仅负面标记** | 声誉不涨权重；只有举报成立/协议违规才降权或隐藏 | ⚠️ 需律师：属于"治理"而非"激励"，但仍是平台改分发 |
| **E 声誉兑换任何东西** | 声誉换额度 / 换折扣 / 换席位 | ❌❌ **结构性禁止**，PRD §9.1 + 既有结构（无 `redeem*`）已封死，本 ADR 不为它开口子 |

### 2.2 我的建议（需律师复核后才算数）

**维持 A；若要做，只做 B。C / E 明确不做。**

三条理由：

1. **A 不是缺陷，是前提。** 我们的整个立场是"Agent 站在用户这边、不拿广告费、不改分发"。按时间排序**就是**这条立场的可执行形式 —— 只要排序可被收买/加权，"我们不卖排序"这句话立刻失去结构支撑。把 A 当成"待补的缺口"去填，等于亲手把护城河填平（R48 的原话：别把维持自己立场的前提条件当成待补的缺陷）。
2. **B 的信息架构是干净的**：筛选器的输入是**公开记录**（本来就是匿名可读的），输出是**用户自己的视图**。平台没有对任何人"加权"，只是把已有的公开事实做成一个开关。用户不点，看到的和今天完全一样。
3. **C 会把 ADR-002 的准入闸变成一门生意**。一旦声誉能换来曝光，`db.keys` 的签发、`label`/`note` 的归属记录、贡献上限 `CONTRIBUTION_CAPS`，全部从"治理工具"变成"配给工具" —— 而我们为了保护这些数据不被滥用，刚刚才把准入闸做成人工签发。

### 2.3 若裁定"做 B"，硬规则（每条都要能写成断言）

1. **默认序不许动**：不加任何参数时，返回结果必须与今天**逐字节一致**（按 `idx` / `created_at` 升序）。守卫按条目切片断言，不搜整份源码。
2. **筛选是客户端参数，不是服务端默认**：端点只在显式传入筛选参数时改变返回集，且响应必须回显"当前是筛选视图"。
3. **筛选只能用公开字段**：能用 `tally`（派生值）、不能用任何内部风控/举报未决状态（那会把"被举报"变成公开污名）。
4. **不出现排序权重**：只允许"过滤"（在/不在），不允许"加权"（乘系数）。过滤是可解释的，加权不可解释 —— 加权是定价的第一步。
5. **声誉仍不落库**：筛选时现算，不新增"分数/余额"表（PRD §9.1 已封死）。
6. **文案不得暗示价值**：不得出现"高价值""优质""推荐"等评价性措辞；只能说"贡献记录 ≥ N"。

## 3. 风险与回滚

| 风险 | 处置 |
|---|---|
| 做了 C 却以为只是"优化排序" | 本 ADR 把 C 与 "触线" 绑定；任何加权实现必须引用本 ADR 的裁定，无裁定即视为越线 |
| B 被悄悄演进成 C | 硬规则 4（只许过滤、不许加权）+ 守卫断言"响应里不存在权重字段" |
| 声誉变成公开污名 | 硬规则 3（只用公开字段，不用举报未决） |
| 律师认定 B 也触线 | 那就只保留 A。**A 永远可回退，因为它就是现状** |
| 回滚 | A 是默认路径；B 是显式参数 ⇒ 去掉参数即回到 A，无数据迁移 |

## 4. 诚实边界

1. **我给不了法律结论。** PRD §9.1 的红线是"权益 vs 证券"的**法律定性**，工程侧只能保证"结构上做不到"，不能保证"法律上没问题"。**这道题必须律师答。**
2. **没有任何外部证据表明"需要排序"。** 当前零真实用户规模（门禁 #28 连"境内月活"的分母都还不可信），"用户需要按声誉找 Agent"是一个**假设**，不是观察。
3. **我不知道 B 会不会也被认定为触线**。我给的理由是"分发权在用户"，但监管口径可能看"平台是否提供了把声誉换成注意力的机制"。这一条我标为**待律师**，不冒充结论。
4. **本 ADR 不动任何代码。** 声望的派生、封顶、不可转让、匿名可读，全部维持现状。
5. **门禁里的位置**：本条与 #22（举报通道）、#28（境内合规重估）相邻但不重叠 —— 那两条管"内容与主体合规"，本条管"分发是否被定价"。若裁定"做 B"，建议新增一条门禁承载它。

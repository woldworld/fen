## 1. 背景与问题

### 1.1 触发事实（2026-10-21 取证，全部可复现）

主人的原话是："两个微信直接发消息，你要注册微信账号。而我们现在是用户填好我们的中转网址，我们就免费给它中转了。"

这句话在代码里**逐字成立**，且是刻意设计的结果，不是漏了个 bug：

| 事实 | 实证 |
|---|---|
| 注册是 **TOFU 自签**：请求用**自带的公钥**给自己验签，先到先得 | `lib/hub/hub.js:816` `selfCred = { pubkey: p.pubkey }`；`lib/core/cloud_service.dart:112-127` 客户端本地生成密钥对后直接 POST |
| 客户端**唯一**的入驻动作就是填一个网址 | `lib/ui/advanced_settings_screen.dart:453` 写入 `cloud_hub_url`；注册由业务流自动触发，无任何凭据输入 |
| `/api/register` **没有任何限流**（同文件 `/api/send` 有） | 对比 `hub.js:1087` 的 `rateLimit(fromId)`；注册块 `801-873` 全程无调用 |
| 身份表**无上限、无邀请码、无邮箱/手机、无「允许注册」开关** | `hub.js:204-218` 的 `db` 骨架里没有 keys 表；`/health` 只能靠 `Object.keys(db.agents).length`（`793`）报数 |
| 限流键是 `agent_id` ⇒ **换 ID 即重置配额** | `hub.js:447`；`hub.js:2092-2094` 注释已自认「agent_id 可任意轮换，每换一个又多 20 轮」 |
| 世界服务器没有第二道门：它只读 hub.json 的身份表 | `lib/hub/world.js:39`（`HUB_FILE`）、`world.js:209-220`（`hubAgents` 按 mtime 重读） |
| 零门槛是**有意**的：onboarding 文案明确鼓励留空跳过 | `lib/l10n/app_localizations_zh.dart:421`「没有也没关系，可以跳过」 |

⇒ 所以这不是"补一个 bug"，是**改一条产品策略**：当初为了让 onboarding 不掉人，把入驻成本压到了零。

### 1.2 为什么现在必须收（三条，按严重度）

1. **合规（最硬）**：一个对公众开放注册、替陌生人长驻转发消息的服务，性质上是「面向公众的信息服务」。门禁 #28 正是挂着的这条，其触发条件之一是「境内月活 > 100」—— 而现在**连分母都不可信**：`db.agents` 里混着任意脚本刷出来的身份，无法回答"到底有多少真实用户"。
2. **滥用**：一个脚本能刷出十万个 `agent_id`，每个 60 次/分钟。总量没有天花板，只有单点天花板。
3. **运营**：没有「账号」概念 ⇒ 无法公告、无法计费、无法封到人（只能封 IP 与 ID），也无法解释某个消息是谁转的。

### 1.3 我先纠正自己一处：「自动发」在本仓不具备前提

起草时我的建议是「key 自动发 + 单邮箱限额」。查证后必须修正：**本仓没有发信通道** —— `lib/hub` 全目录 `nodemailer` / `smtp` / `sendmail` / `mailgun` **零命中**，也没有任何短信服务。

没有发信通道时，"自动发"只能退化成「客户端点一下就领到 key」，那与「填个网址就注册」**没有本质差别**，只是多跳一个页面 —— 它挡不住脚本，只能算摩擦。而主人的原话是「**申请** apikey」，申请意味着有人批。

⇒ 本 ADR 据此把默认形态定为 **人工签发**（运营方一条命令发 N 个 key），把「自助申领」做成**默认关闭**的开关，等真有发信通道或真有量了再开。这一处偏离已在 §7 诚实边界列明。

## 2. 决策

> **官方中转站默认要求注册持有签发的访问 Key；自建 / 局域网实例默认不要求（双轨）。** Key 只是**注册前置闸**，不替代消息签名 —— 签名仍走既有 Ed25519 信封。

### 2.1 硬规则（每条都要能写成断言）

1. **闸位只在注册口**：`POST /api/register` 前置校验。`/api/send`、`/api/mailbox`、`/api/a2a/*`、`/api/world/*` 的**签名协议一字不改**（R8：协议算法全项目一份，不得为收费/准入引入第二套签名）。
2. **三态开关**：`HUB_REGISTRATION` = `open`（默认）/ `key` / `closed`。源码默认 `open`，保证**自建开箱即用**；官方部署由 `lib/hub/deploy/install-server.ps1` **显式**写入 `set HUB_REGISTRATION=key`，并配守卫断言（部署包内 `run-hub.cmd` 必须含该行，否则 FAIL）。★ 不许靠"改默认值"来区分官方与自建 —— 这是本仓反复踩过的「改了默认值漏了显式实例」。★ 2026-10-21 实现违反过此条（`install-server.ps1` 写成了默认 `key`），**复查时已订正**。实际后果很硬：官方服务器也用这个包部署 ⇒ 任何人**重跑一次一键部署**就会把官方站静默切闸，而老客户端不认识 Key ⇒ 直接违反本 ADR 规则 10。
3. **拒绝必须按 `error` 码区分，不许只判 HTTP 状态**：`403` 现在有两种含义 —— `identity_conflict`（该 ID 上绑了别的公钥）与新加的 `registration_key_required` / `key_invalid` / `key_revoked`。客户端分支一律读 `error` 字段。★ 只判 403 就是把两种完全不同的处置（走 ROTATE / 去要 key）混成一锅。
4. **Key 只存哈希，明文只出现一次**：`db.keys` 存 `sha256(key)` 的 hex，明文仅在签发命令的 stdout 打印**一次**。签发/吊销走 hub 的 `/api/admin/keys`（需 `X-Admin-Key`），`keygen.js` 只是 **HTTP 瘦客户端**，**不直接写 `hub.json`**。★ 这条相比草案**改过**：草案写的是「本地改文件、不需要 admin key」，实现时发现 hub 进程**常驻 `db` 并 `saveSoon()` 回写** ⇒ 第二个写者直接改盘会被旧快照吞掉（签了的 key 重启后就没了）。
5. **一 Key 一身份**：Key 首次使用即绑定 `did` + `agent_id`；之后拿同一个 Key 注册**另一个** did ⇒ `409 key_already_bound`。换机/换钥走既有的 `POST /api/identity/rotate`（R1：带证明换钥，绝不自动签名），**不走重新注册**。
6. **存量身份豁免（grandfather）**：`db.agents` 里**没有** `key_id` 字段的已有身份，重注册照旧放行（视为历史用户），但**不得借豁免换 did**。豁免只对已存在的 `agent_id` 生效，新 `agent_id` 一律要 key。
7. **吊销必须双向落，否则闸只挡新来的**：
   - `db.keys.<key_id>.status = 'revoked'` + `revoked_at`
   - `db.agents.<agent_id>.revoked_at = <ts>`（并清空 `key_id`）
   - `authAnyRegistered`（`hub.js:543`）、`/api/send`（`1080`）、`/api/mailbox`（`1110`）三处判 `agent.revoked_at` ⇒ 立即拒绝
   - ★ 世界服务器**不读** keys 表（保持「只读 hub.json 一份」的既有架构），它只判 `agent.revoked_at` ⇒ 所以**吊销必须写进 agents 记录**，否则 world 侧永远拦不住。这条是本 ADR 最容易做一半的地方。
8. **自助申领默认关**：`HUB_KEY_SELF_SERVE=1` 才开 `POST /api/key/apply`，且按 IP 日配额限发。默认关闭 ⇒ 默认形态是真门槛。
9. **五语种同步**（R7）：新增文案在 `app_en/zh/zh_Hant/ja/vi` 五个 ARB **同步增减**，不要求数量相等。
10. **发布顺序：手机先于服务器**。老客户端不认识 key ⇒ 若服务器先切 `key`，会把所有新用户挡在门外且给出**错误提示**（403 被读成 identity_conflict）。故顺序钉死：出含 key 输入的客户端 → 再切官方站。★ 这与 PRD §14.3「服务器必须先于手机升级」是**反向例外**，理由不同（那次是协议兼容，这次是准入策略），必须在交付记录里写明，免得后来人照抄错顺序。

### 2.2 数据形态

```
db.keys = {
  "KEY-3f9a2c14": {
    key_id, hash,            // sha256(key) hex，明文不入库
    label, note,             // "邀请-2026-11-校友群" —— 归属可追溯（门禁 #28 要的分母）
    status: 'active' | 'revoked',
    created_at, revoked_at,
    bound_did, bound_agent_id
  }
}
db.agents.<id>.key_id   = "KEY-…"   // 缺该字段 = 存量豁免
db.agents.<id>.revoked_at = ts      // 吊销后置位；world 侧唯一判据
```

Key 明文形态：`WK-` + 4 组 5 位 Crockford Base32（≈100 bit 熵），与既有的 `AG-` 前缀**视觉可分**，防止用户贴错字段。

### 2.3 签发与吊销（运营侧）

- `node keygen.js issue --n 5 --label "邀请-2026-11"` ⇒ stdout 打印 5 条明文 key（一次性）
- `node keygen.js list` / `node keygen.js revoke KEY-3f9a2c14b7`
- 环境变量 `HUB_ADMIN_KEY`（与 hub.js 一致）+ `HUB_URL`（默认 `http://127.0.0.1:3000`）

> **★ 实施时改掉的一处设计（原稿是"直接读写同一个 hub.json"）**
>
> 原稿让 `keygen.js` 复用 `HUB_DATA_DIR` 直接改 hub.json。实施时发现这是**两个写者同一个文件**：
> hub.js 把整份 db 装在内存里，任何一次 `saveSoon()` 都会用旧快照整份写回 —— 线下签发完的票，
> 下一次心跳就被抹掉，而现场表现是"**发出去的票全都无效**"，且没有任何一处日志会说原因。
>
> ⇒ 改为：**唯一写者永远是 hub 进程**，签发工具降级成瘦客户端，走三个受 `HUB_ADMIN_KEY` 保护的端点
> （`POST/GET /api/admin/keys`、`DELETE /api/admin/keys/<key_id>`）。代价是多三个端点，
> 收益是"票发出去就得算数"这件事由结构保证，而不是由操作规程保证。

## 3. 备选方案

| 方案 | 判断 | 理由 |
|---|---|---|
| **C 双轨（官方要 key / 自建免 key）** | ✅ **采纳** | 保住「你自己搭一个就能用」的开源承诺；闸只加在公共面上，与 R4「局域网≠公网」的分层同构 |
| A 只加开关、一键关掉公开注册 | ❌ 否决 | 没有发放渠道 ⇒ 官方站一关就是"谁都进不来"，老用户升级即掉线；不是准入，是停业 |
| B 全员申请（自建也要 key） | ❌ 否决 | 直接砍掉开源版的自建价值；且与门禁 #27「自建 Hub 接入协议」尚未成文相冲突（还没定契约就先加锁） |
| D 邮箱/手机验证后发 key | ❌ 当前不具备 | 无发信通道（§1.3）；引入 SMTP 或短信 = **新增外部依赖**，本身要另过一份 ADR，且会把境内合规面进一步放大 |
| E 用 Ed25519 身份本身当闸（自签即准入） | ❌ 否决 | 这就是现状。自签无法区分"我们邀请的人"与"脚本" |
| F 接第三方身份（GitHub OAuth 等） | ❌ 否决 | 新增外部依赖 + 第三方 SDK 进入客户端 → 隐私政策 §8.1 要改、离线自足要破，代价远大于收益 |

## 5. 风险与回滚

| 风险 | 处置 |
|---|---|
| 官方站忘配 `HUB_REGISTRATION=key` ⇒ 闸形同虚设 | 硬规则 2 的守卫断言 + 启动日志打一行「hub 注册模式=key」，运营方扫一眼日志即可核对 |
| 吊销只改了 keys 表、没写进 agents ⇒ world 侧仍能发言 | 硬规则 7 的双向落 + 守卫断言「吊销后 world 侧必须拒」 |
| 客户端只判 HTTP 403 ⇒ 把「去要 key」误报成「身份冲突」 | 硬规则 3；老客户端过渡期只影响新用户，故发布顺序见硬规则 10 |
| 存量用户被误挡 | 硬规则 6（缺 `key_id` 即豁免）+ 守卫断言「无 key_id 的存量身份可重注册」 |
| Key 被转让/泄露 | 一 key 一 did（硬规则 5）⇒ 拿到 key 也只能绑一个身份；吊销即时生效 |
| 自助申领被脚本刷 | 默认关；开启时按 IP 日配额；且明示它**不是**实名闸 |
| 回滚 | 把 `HUB_REGISTRATION` 改回 `open` 即回到今天的行为；`db.keys` 留着不影响（客户端带不存在的 key 会被忽略） |

★ **第二个被自家守卫抓住的缺陷（存储键守卫 `verify_data_keys.dart`）**：新增
`CloudService.prefsHubAccessKey` 时写的是 `static const prefsHubAccessKey = 'cloud_hub_key';`
——省略 `String` 类型。该守卫的常量表只认 `const String name = '…'`，于是这个键被判成
**动态键**，逼着去 `_expectedDynamic` 里登记一行才放行。**登记 = 放宽守卫**：一旦进了动态键清单，
"读了这个键有没有人写"就再也不会被检查。正确处置是**补类型**（`static const String …`），
让它落回字面量集合、继续受"有读必有写"约束 —— 收紧而不是放宽。
教训泛化：**守卫把你拦下来时，先问"它是在要我放宽还是提醒我写规范"。** 这轮差一步就走反。

★ **正控已做**：把 `world.js` 的吊销判定改名成 `agent.revoked_at_disabled`，守卫当场变红
（`FAIL F1`）—— 顺带暴露了守卫自己的一个缺陷：原先用 `includes('agent.revoked_at')` 判，
改名后的标识符**字面包含**该子串，毒注进去仍然全绿。已改成词边界正则 `\bagent\.revoked_at\b`。
这条记在这里是因为它属于"**判据查错了对象**"的同族问题，而不是笔误。

★ **第三个自抓缺陷（同一病症的第三次现形：判据查错了对象）**：官方站开闸的唯一受支持入口是
`1-一键部署.cmd -Registration key`，但那个 `.cmd` **不是手写文件** —— 它由 `make-package.ps1`
里的 here-string 生成，而且打完包还会把产物**反向覆盖**回 `deploy/`。复查时我直接改了
`deploy/1-一键部署.cmd`（产物），守卫也读那份产物 ⇒ 改完 78 条全绿，**一跑打包就被模板盖回原样**，
守卫随即又绿（因为它读的还是被改过的产物，直到打包把它冲掉）。同族问题第三次现形后，
判据拆成两层：**源头判据查生成器**（K1/K2 读 `make-package.ps1`）、**产物判据只抓"改了模板没重打包"**
（K2b）。教训：凡"某文件是不是符合要求"，先问**这个文件是人写的还是机器生成的**；
机器生成的东西，改它等于改缓存。

**已完成**：版本 bump（0.117.0+1 → 0.118.0+1）、APK 重出（33,497,581 B）、部署包重打、导出树重生成、本地提交。**未做**：推送 GitHub（需主人点头）、官方站真正切 `key`（须等 App 铺开）。所以本 ADR 应读成"**已实施、已出包、未发布**"。

## 7. 诚实边界

1. **「自动发」被我改成了「人工签发」**：因为本仓无发信通道（§1.3）。自助申领端点会写进代码但**默认关闭**。若主人坚持要自动发放，打开那个开关即可生效，但请知悉：它只是摩擦，不是门槛。
2. **它挡不住什么**：持有一条合法 key 的用户，用脚本刷消息仍受既有速率闸（60 次/分钟、20 条/小时）约束，本条**不新增**内容级审核。内容合规仍归门禁 #22（举报通道）与 #28。
3. **它不解决「自建 Hub 怎么接入官方网络」**：那是门禁 #27，需要一份独立的接入协议（许可范围 / 收费 / 品牌边界 / 终止条款）。本 ADR 只回答「官方站收谁」，不回答「自建者怎么入网」。
4. **离线/局域网直连完全不受影响**：双轨的前提就是「闸只加在公共面」。若将来有人把 key 检查做进局域网直连路径，等于破坏产品红线，属实现错误。
5. **门禁 #28 的分母问题只被改善，未被解决**：有了 `label`/`note` 能回答"这批 key 发给了谁"，但「境内月活 > 100」仍需要真实的活跃统计口径（现无）。本条不冒充合规结论。
6. **未做**：Key 轮换（用户换 key）、Key 配额分档（免费/付费）、按 key 计费 —— 均属 C 档商业化材料，收费前另议。

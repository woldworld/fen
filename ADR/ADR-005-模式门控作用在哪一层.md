## 1. 背景：一次搬迁把「门控语义」这个空白暴露了

0.120.0 把控制中心的六项系统能力迁进管理页的「系统与能力」区块，并让整块
`if (!mode.simpleMode)` 门控 —— 入门（默认）模式不渲染。

搬迁本身是干净的（62 个 l10n key 逐条追踪，22 迁入 / 39 保留 / 1 在高级设置，算术自洽）。
但事后审计发现一个**从未被定义**的问题：**"仅进阶模式"到底约束谁？**

### 1.1 取证（全部核到行号）

| 事实 | 实证 |
|---|---|
| 页面打开**不检查模式** | `lib/core/app_navigation.dart:61-72`：`openAppPage(key)` 只做「查表 → 拿 Navigator → push」，**零处** `simpleMode` |
| 页面注册**与模式无关** | `lib/main.dart:180` 无条件 `registerAppPages(buildAppPages())` |
| 注册表里就有本轮被门控的页 | `lib/ui/app_pages.dart:64-71`（`phone_control` / `notify_sms`）、`:95-100`（`weekly_report`） |
| 工具的契约本来是"只导航" | `lib/core/agent_service.dart:587-591`：「`open_app_page` **只把页面推到前台，不改任何设置**」；隐私能力「必须主人亲自开启总开关」 |
| 真正的门是三道总开关 | `lib/core/app_navigation.dart:86-90`：`mail` / `phone_control` / `notify_sms` 各自的开关，**默认全关**，且关 ⇒ 工具压根不注册 |
| 门控只写在 UI 里 | `lib/ui/manage_screen.dart:180-182` —— ★ 这是 **0.120.0 时的位置**，本轮已把门控下沉到区块内部，同几行现在是"整块常显"的注释（引证行号会漂移，故此处标明时点）：`if (!mode.simpleMode) ...[ _buildSystemCapabilitySection(…) ]` |

⇒ 现状是：**入门模式用户自己点不到「系统与能力」，但对智能体说"打开手机控制"，页面照样推上来。**
这不是崩溃级别的 bug，是一处**语义空白**：门控只说"不渲染"，没说"不许到达"。

### 1.2 为什么必须现在定

因为下一轮一定有人（可能是我）为了让"入门模式更干净"，顺手给 `openAppPage` 加一句
`if (simpleMode) return 'not available in beginner mode';`。那一改会同时动三样东西：
智能体的可达页面集合、KB 的路径描述、以及"能力是否存在"的判断口径 —— 属于边界变更。
不先定死，就会在代码里悄悄发生。

## 2. 决策：门控只作用于「入口可见性」这一层

模式（Beginner / Advanced）**只决定"人自己能点到的入口有多少"**，不决定：
- 智能体能不能代开某个页面（`open_app_page` 不受模式约束）；
- 某项能力是否存在（能力由**各自的开关**决定，与模式无关）；
- 服务端行为（模式是纯客户端概念，服务端零感知）。

### 2.1 备选方案

| 方案 | 内容 | 判据 |
|---|---|---|
| **A 门控只管可见性**（采纳） | `openAppPage` 维持现状；把"仅进阶"的语义在文案/KB 里写清（"入门模式收起，可让智能体代开"）；同时把**需要主人授权的两项下沉为常显** | ✅ 与 `agent_service.dart:587` 既有契约一致；不新增失败面 |
| **B 给 `openAppPage` 加模式门控** | 入门模式拒绝打开"进阶页"，回一句话给模型 | ❌ 制造新的失败面：模型要解释"你在入门模式"，而模式的切换入口在工具栏 —— 用户被绕进一个和目的无关的迷宫 |
| **C 只给隐私能力页加门控** | `mail` / `phone_control` / `notify_sms` 三页在入门模式拒绝代开 | ❌ 与 A 的理由冲突，且这三页恰恰是"必须主人亲自授权"的页 —— 把它们挡在门外，等于把"主人亲自授权"的机会也挡掉 |

### 2.2 采纳 A 的理由（三条，都是结构性的）

1. **工具的契约本来就是"只导航"。** `open_app_page` 不写任何设置（`agent_service.dart:587`），
   所以"打开一个页面"在能力语义上等于零 —— 它不授予任何东西。给它加模式门控，
   是把一个纯导航动作当成权限动作来管，管的层错了。
2. **真正的门是三道总开关，而且默认全关。** `mail` / `phone_control` / `notify_sms`
   的开关关着时工具**压根不注册**（`app_navigation.dart:86-90` 注释明写）。所以"页面可达"
   与"能力可用"之间隔着一道主人亲自按的开关。门控加在页面上，是给已经锁好的门再加一把挂锁，
   代价是主人自己也更难进去。
3. **入门用户通过智能体打开某个进阶页，说明他需要它。** 此时正确的行为是"让他能开"，
   不是"拒绝并解释为什么拒绝"。模式的目的是**少给选择**，不是**少给能力** ——
   这两件事一旦混同，产品就会开始替用户做决定。

### 2.3 本轮据此做的两个改动（同批落地，不回退）

1. **把"需要主人授权"的两项下沉为常显**：通知设置（含通知权限授予）与系统日历（含只读授权）
   **在任何模式都渲染**；其余四项（设备控制 / 通知与短信 / 语音播报 / 智能体周报）仍只在进阶模式展开。
   理由：授权入口不是"调参入口"，藏起来等于让主人无法完成授权 —— 这与 `R14` 同族，
   但更严重：`R14` 管的是"开关没盖住所有消费路径"，这里管的是"开关本身没有入口"。
2. **文案与 KB 同步改口径**：`manageSystemCapabilityHint` 不再写"从控制中心迁入，仅进阶模式显示"
   （那是给开发者看的），改为说"改动立刻生效；通知与日历的授权随时可调整"；另新增
   `manageSystemCapabilityHintSimple`（五语种）说明"通知与日历的授权随时可改；其余能力切到
   进阶模式后展开" —— **两套口径而不是一句通用话**：进阶模式下说"其余在进阶展开"是错的
   （它就在眼前），入门模式下不说又等于让人找不到。KB 侧同步：`morning_greeting` /
   `notifications_mute` / `system_calendar` 三条去掉 `(Advanced mode)`，
   `full_mode` 补「通知与日历授权卡两模式都在」，`kbVersion` **31 → 32**。

## 3. 硬规则（每条都能写成断言）

1. **模式不得出现在导航层**：`lib/core/app_navigation.dart` 里不得出现 `simpleMode` /
   `ThemeProvider` 一类模式判断；`openAppPage` 的入参只有页面键。
   （断言：该文件 `simpleMode` 命中数 = 0。）
2. **模式只允许出现在 UI 的 build 路径里**：新增任何模式门控，必须落在某个 `build` 内，
   且门控的对象是**入口**（卡片/按钮/区块），不是页面本身。
3. **"需要主人授权的能力"必须有一个非门控入口**：凡调用 `requestPermission()` 的 UI 点，
   其所在 widget 不得被任何模式门控整体包住。
   （断言：`_NotifySettingsCard` / `_CalendarSettingsCard` 在 `manage_screen.dart` 中的
   出现位置不在任何 `if (!mode.simpleMode)` 块内 —— 由 `verify_mode_visibility.dart` 反向钉住。）
4. **页面可达 ≠ 能力可用**：智能体回报里必须区分这两件事（已有 `privacyCapabilityNote` 机制，
   `app_navigation.dart:106`；不得退化）。
5. **服务端零感知模式**：任何 hub / world 端代码不得读取或推断客户端模式。

## 4. 风险与回滚

| 风险 | 处置 |
|---|---|
| A 被误解成"门控不重要" | 硬规则 2：门控仍然存在，只是层级被限定在 UI 入口 |
| 智能体把入门用户带进进阶页后，用户在页里被一堆参数淹没 | 页面自解释（区块标题 + hint 已说明"其余能力在进阶模式展开"）；后续如需可加页内提示条，本 ADR 不要求 |
| 有人后来给 `openAppPage` 加门控 | 硬规则 1 的断言（`simpleMode` 命中 0）当场变红 |
| 回滚 | 方案 A 即现状，无数据迁移；改动只在 UI 文案与门控粒度，去掉即回到 0.120.0 行为 |

## 5. 诚实边界

1. **本轮没有做真机验证**（本环境无设备）：通知权限与日历授权在入门模式可达，是代码路径上的
   "可达"，没有在 Android 13+ 真机上点过一遍。
2. **"授权入口必须常显"是我的判断，不是主人的原话。** 主人说的是"日常的留在控制中心"，
   我把它读成"需要主人亲自按的开关不能藏"。若主人认为通知/日历也该收进进阶，本 ADR 的
   §2.3-1 可以单独回退，不影响方案 A 的结论。
3. **本 ADR 不解决"入门模式太简陋"这个更大的问题**（另有记录）。它只回答"门控作用在哪一层"。
4. **ADR 不替代门禁**：本条的约束靠 §3 的断言与两条守卫（`verify_mode_visibility` /
   `verify_settings_split`）承载，不新增门禁编号。

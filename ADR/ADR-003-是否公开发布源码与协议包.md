## 1. 背景与问题

### 1.1 触发：我们正在对读 llms.txt 的 Agent 撒一个"这不是死链"的谎

上一轮（`0909410`）修掉了 `landing/dist/llms.txt` 第 3 行的一个**死链**：原本写

```
Open source: https://github.com/woldworld/dahuang
```

而 `dahuang` 是**已退役品牌**，仓库实测 **404**。按 ADR-001 规则①与 §1.1 先例（死链一律换站内永远可达页），改为：

```
Source: not publicly published yet (publication pending) · protocol & verifiability: https://wold.world/docs/
```

这句话现在**是真的**。但它同时承认了一件事：**源码根本没有发布。**

llms.txt 是专门给 LLM / Agent 读的机器可读文件。它的第 3 行在回答"你的源码在哪，我怎么核验你说的可验证性"。我们现在只能回答"还没发"。而官网 `/docs/`、`/self-host/`、`/security/` 上写着 `Client MIT licensed, protocol CC-BY-4.0` —— **声明的许可与实际可获取的代码之间有一个洞**。

⇒ 所以本 ADR 的问题不是"要不要修一个链接"，而是：**那个链接该不该存在。**

### 1.2 现状取证（2026-10-22，全部可复现）

| 事实 | 实证 |
|---|---|
| 主仓**没有远端** | `git remote -v` 输出为空 |
| GitHub `woldworld/fen` 实测 **404** | 直接请求 |
| GitHub `woldworld/dahuang` 实测 **404** | 同上（退役品牌） |
| npm `@woldworld/protocol` 实测 **404** | 直接请求 |
| **公开面其实已经备好了** | `opensource-release/`：1 个提交 `50be981`、**650** 个 tracked 文件、盘上 1,358 文件 / 50,466,599 B |
| 且**与主仓同版** | 导出树 `pubspec.yaml` = `0.118.0+1`，主仓同值（R34 那次"落后 53 版"的问题已不再成立） |
| 私有层**零外泄** | 导出树内 `lib/hub` / `lib/dist` / `备份` / `repo-content` / `.workbuddy` / `tool/_` 各 **0** 个文件（R13 成立） |
| 协议包已可发 | `packages/protocol`：`@woldworld/protocol` v0.1.0、`license: MIT`、**零依赖**、`files` 白名单只含 `src/` + `index.d.ts` + README + LICENSE；`verify_protocol_package.js` **42 条** |
| 官网的仓库地址是**死数据** | `landing/data/site.json` 的 `repoUrl = https://github.com/woldworld/fen`，但 `landing/build.js` 对它**零引用** —— 不渲染，所以线上没有死链（只有 llms.txt 那行曾经有） |

### 1.3 本轮已顺手修掉的一处"最容易来不及"的地方

导出树的首条提交信息，原本由 `opensource_release.ps1` 第 441 行写成：

```
DahuangAI v0.118.0+1 — first public release
```

以及第 16 / 36 / 37 行的用法示例、默认作者名、默认作者邮箱，全部是退役品牌。导出树的 `.git/config` 里也留着 `DahuangAI contributors <dahuang-ai@users.noreply.github.com>`。

★ **为什么必须改管道而不是改产物**：`opensource-release/` 是 robocopy + git **生成**的树，那条提交信息每次导出都会重写。手改那条提交 = 改缓存，下次导出就复原（ADR-002 §6「第三个自抓缺陷」同族）。**而这条信息一旦推送就永久留在公开历史里** —— 这是整件事里唯一一处"改起来最便宜、又最后一次能改"的地方。

本轮已改：管道 4 处 + 导出树 `.git/config` + 用新身份 `--reset-author` 重建那唯一一条提交。守卫 `verify_opensource_release.js` 从 24 条扩到 **31 条**（新增 ④ 组：管道不得含退役品牌、导出树首提交信息不得含退役品牌，共 7 条，含 3 条正控；下毒实测会红）。

## 2. 决策（待主人裁定）

> **是否把「源码 / 协议包」真正发布出去；若发布，发布哪一层、发到哪个渠道。**

### 2.1 备选方案

| 方案 | 内容 | 判断 |
|---|---|---|
| **A 不发布**（现状） | 维持 llms.txt 写"尚未发布" | 诚实但**自相矛盾**：官网承诺 MIT/CC-BY-4.0，代码却取不到。**门禁 #24 永远"未满足"** |
| **B 只发协议包** | `packages/protocol` → npm `@woldworld/protocol` | 暴露面**最小**：只有协议算法（信封/canonical/base58/did/Ed25519/Merkle/贡献/房间角色），**不含任何 UI、业务、hub 服务端** |
| **C 只发整树** | `opensource-release/` → GitHub `woldworld/fen` | 兑现"客户端 MIT"，但一次出去 **650** 个文件（含 `landing/`、`tool/`、`android/`、`fdroid/`） |
| **D B + C 都发** | 协议包 + 整树 | 最完整；也最不可逆 |
| **E 发但换许可** | 改成"源码可见、非商用" | ❌ **不可行**：官网已公开声明 MIT / CC-BY-4.0，改许可与既有声明冲突，且不可追溯撤回 |

### 2.2 我的建议（需主人裁，不代替决策）

**先 B，观察，再决定 C。** 四条理由：

1. **B 的暴露面与收益之比最好**：协议包是**纯算法、零依赖、零状态**，不含 hub 的准入闸（ADR-002）、不含试用代调、不含任何 Key / 账号逻辑。它恰好兑现 llms.txt 那句 "protocol & verifiability" —— Agent 能真的 `npm i` 下来自己验签。
2. **B 才让"可验证性"从形容词变成动词**：现在我们的可验证性主张，第三方只能读文档相信；发了包，第三方能**离线复算**。这是 §16 透明日志、ADR-002 双向吊销这些设计真正被外部检验的唯一入口。
3. **C 的成本不是"发"，是"以后每版都要发"**：650 文件的快照会持续漂移（R34 的教训就是快照落后 53 版）。没有 CI 自动导出 + 版本对账，C 一发就开始烂。
4. **B 的不可逆代价比 C 小一个量级**：npm 包发错了可以 `deprecate`（版本永久存在但可标记），GitHub 整树公开后连历史都收不回。

### 2.3 若裁定"发"，硬规则（每条都要能写成断言）

1. **先跑门禁再发**：`verify_opensource_release.js`（31 条）与 `verify_protocol_package.js`（42 条）必须全绿；发布前额外跑一次全仓密钥扫描。
2. **导出树版本必须等于主仓版本**，且**本轮之后新增一条**：不能只对版本号 —— `landing/build.js` 这类被本轮改过的文件也必须与主仓**逐字节一致**。当前 `verify_opensource_release.js` 只比 `pubspec.yaml` 的版本串，**查不出内容漂移**（R34 那次的"落后 53 版"就是版本号相同、内容陈旧之外的另一种形态）。★ **该偏差已于 2026-10-23 消除**：`opensource_release.ps1` 已不带 `-RemoteUrl` 重跑，
  新树 `da07bfa`（656 tracked / 31,248,030 B / pubspec `0.119.0+1` / 私有层 **0** 文件 /
  `verify_opensource_release.js` **31 PASS / 0 FAIL** / `CHANGELOG.md` 863,264 B 与主仓
  **逐字节相同**，含本轮 APK 字节与终态读数）。
  ★ 附带实测：重跑**只改文档**（CHANGELOG 定稿）未改 `.dart` ⇒ 全项目
  `flutter analyze` 仍为 **2,000** info，与提交记录一致 ⇒ **不触发**收口技能 §27.1 的
  「改 CHANGELOG ⇒ 重打包」循环（这是"导出树重跑"能否在收口后安全补做的前提）。
3. **提交身份与信息不得含退役品牌**：由 ④ 组守卫钉死（本轮已加）。
4. **不许手改导出树**：一切修改回到 `opensource_release.ps1`，改完重跑导出。
5. **发布后同步回写 llms.txt 第 3 行**：从"not publicly published yet"改回真链接，并把 `Source:` 行纳入守卫（判据从"不得指向 404"改成"必须指向已发布的真地址"）。
6. **发布是主人的动作，不是工程的动作**：本 ADR 通过后，工程侧只负责"把树准备到可推"，`git push` / `npm publish` 由主人执行或显式授权。

7. **公开面不得有指向内部文档的悬空引用**（2026-10-23 实测，此前未登记）：导出树
   `CHANGELOG.md` 含 **67 处**「交付记录 / 交付与验收」字样，`tool/verify_deploy_site_freshness.js`
   等 4 个工程文件也引用 `lib/大荒M1_M2交付与验收记录.md` —— 而交付记录与 PRD **按纪律不进
   公开面**（已在导出树外，实测 `OUT`）。外部读者点不到被引文档，且这些引用会随历史节永久
   累积。发布前必须三选一并写进本 ADR §5：
   ① 公开面改用中性措辞（如"内部交付记录，不随源码公开"）—— 需改 CHANGELOG 历史节措辞；
   ② 把交付记录一并纳入公开面 —— 必须先过 R13（永不外发清单）复核，我不建议；
   ③ 在 README 显式声明"本仓 CHANGELOG 引用的内部交付记录不在公开面" —— 成本最低。
   **未处置前不得推送**（R51：首条公开提交一推送即永久）。
   ★ **2026-10-23 处置（主人裁定"发"后当场执行）⇒ 选 ③。** `opensource/README.md` 新增
   「About internal documents / 关于内部文档」一节（双语）：说明这几份文档是**维护者内部
   记录、不随源码发布、点不到是刻意为之而不是死链**，并承诺"凡涉及行为与契约的结论，
   本仓都有实现/测试/守卫可复核"。
   - **为什么不选 ①**：改 CHANGELOG 历史节措辞 = 改历史记录，而且 CHANGELOG 一变就要
     重打站点与部署包（整链），代价远大于收益。
   - **为什么不选 ②**：交付记录含大量内部审计、排期与运营细节，纳入公开面须先过 R13 复核，
     且会把"内部口径"永久公开。
   - ★ **实测复核（2026-10-23）**：导出树 `CHANGELOG.md` 现为 **69 处**「交付记录」
     （登记的 67 已过期 —— 0.120.0 / 0.121.0 两轮新节也提到它；**这类数字会自己变旧**，R39）；
     引用内部文档名的文件 **6 个**：`CHANGELOG.md`、`ADR/ADR-003`、`ADR/ADR-004`、
     `lib/邮箱工具-实现方案.md`、`lib/compliance/上线合规门槛清单.md`、
     `tool/verify_deploy_site_freshness.js`。README 的一句总声明**覆盖全部 6 个**。
   - ⚠️ 判据强度说明：这一条目前**没有自动断言**（"公开面不得出现指向树外文档的引用"需要
     一份"允许引用清单"，属可选增强）。它是**人工复核项**，已在此写明复核方法：
     扫导出树里所有提到内部文档名的文件，逐个确认被引文档是否在树内。

## 3. 风险与回滚

| 风险 | 处置 |
|---|---|
| npm 包名被抢注 / scope 不归我们 | **发布前必须先确认 `@woldworld` scope 已注册且归本方**；否则改名会破坏 `repository` 字段与文档引用 |
| 公开后出现"我们改许可"的指控 | 许可已在官网公布，**只发不改**；E 方案已否决 |
| 导出树快照漂移（发了旧的） | 硬规则 2 + 每次发布重跑管道 |
| 公开面上有不该公开的内容 | 三层防护（robocopy 排除 / 发布面断言 / 敏感扫描）已是既有设计；本轮复核私有层为 0 |
| 公开后收到大量 issue 拖垮开发节奏 | 属运营决策，不在本 ADR 范围；可先只发协议包（B）降低面 |
| 回滚 | A 案随时可回（不推就是不发）；**已推送/已 publish 的不可回滚**，只能追加新版本或 deprecate |

## 4. 诚实边界

1. **我不知道 `woldworld` 这个 GitHub 组织 / npm scope 是否归我们**。我在离线环境无法核实归属，只能确认"这两个地址现在都不存在"。
2. **我无法判断"开源是否对商业有利"**。那是主人的商业判断；我给出的 B 先于 C 只是**工程与风险**视角，不含市场判断。
3. **本轮没有推送任何东西**。`git remote -v` 仍为空，导出树仍是本地目录，npm 上仍然没有这个包。本 ADR 是**文档**，不是执行。
4. **`landing/data/site.json` 的 `repoUrl` 我没有改**。它是死数据（零引用），但一旦将来有人开始渲染它，就会立刻变成死链 —— 建议在发布决策里一并处理（要么删字段，要么等真发布后填真地址）。
5. **APK 分发渠道（F-Droid 等）不在本 ADR 内**。`fdroid/` 目录在导出树里，但那是另一条发布通道，需独立决策。
6. **公开面仍有 32 处退役品牌 `DahuangAI` 字符串，本轮只清了"门面"，其余是已披露的遗留。**
   2026-10-23 推送前实测（导出树逐文件扫 `\bDahuangAI\b`）：本轮改掉的是**门面三处** ——
   `opensource/README.md` 标题与正文、`opensource/CONTRIBUTING.md` 标题（这三个在 `opensource/`
   叠加目录里，不进主仓源码 ⇒ 不改 `.dart`、不触发 MINOR bump、不影响 APK 与站点）。
   **仍留着的**分三类，都不在本轮范围：
   - **历史记录**：`CHANGELOG.md` 里那些"我们如何修掉退役品牌"的条目 —— 删掉等于抹历史，保留；
   - **守卫代码本身**：`tool/verify_landing_machinereadable.js` 的负控注入串与注释、
     `tool/verify_opensource_release.js` 的 `RETIRED_RE` —— 这些是**判据**，改了就瞎；
   - **源码内部字符串**：`lib/core/system_knowledge.dart`（工具描述，用户可见）、
     `lib/l10n/app_en.arb` 九条 ROM 引导（写法是 `Dahuang AI` 带空格，词边界判据不匹配）、
     `linux/runner/my_application.cc` 两处窗口标题、`pubspec.yaml` 的 `description`。
     ⇒ **要清这些必须动 `.dart` / ARB ⇒ MINOR bump + 重出 APK + 重打包 + 重跑导出树**，
     属**独立一轮**（建议 0.122.0），不在"推第一次"的路径上。**公开后它们会永久留在首提交里**，
     这是知情选择，不是遗漏。
